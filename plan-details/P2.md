## Step 1 — Comfort overlay window (2.1a: warm filter) `[ ]`

**Goal:** A full-screen, click-through, always-on-top overlay window tinting the screen warm (f.lux-style) with a subtle paper-grain, intensity adjustable.

**Files:** `aegis-ui/src-tauri/src/lib.rs` (window creation + commands), new `aegis-ui/src/overlay.html` (static page, no React needed)

**Instructions:**
1. Create `overlay.html` (put in `aegis-ui/public/`): a single fullscreen `<div>` with:
   - warm tint: `background: rgba(255, 147, 41, VAR)` where VAR is set via JS from a query/event; use `mix-blend-mode: multiply` NOT supported on a transparent webview over the desktop — instead use a plain translucent orange layer (works everywhere).
   - grain: SVG `feTurbulence` noise as a data-URI background, `opacity: 0.05`, `background-size: 280px`.
2. In `lib.rs` add commands:
   - `overlay_enable(app: AppHandle)`: build a `WebviewWindow` labeled `"overlay"` with `.fullscreen(true)` (or `.maximized(true)` + `.decorations(false)`), `.transparent(true)`, `.always_on_top(true)`, `.skip_taskbar(true)`, `.focused(false)`, url `overlay.html`. Then `window.set_ignore_cursor_events(true)` — **this is the click-through key**.
   - `overlay_disable(app)`: close the window if it exists.
   - `overlay_set_warmth(app, warmth: f32)` (0.0–0.6): `window.eval(&format!("setWarmth({})", warmth))` calling a JS fn in overlay.html.
3. Transparency needs `"windows": [...]` config or runtime builder args; on Linux also ensure the `tauri.conf.json` app > `withGlobalTauri` irrelevant — but WebKitGTK transparency works when `transparent: true` and the page body background is transparent.
4. Auto-warmth scheduler: a `tokio` task (spawned when overlay enabled) computing warmth from local hour: 0.0 before 17:00 → ramp to 0.35 by 22:00 → hold till 05:00. `chrono` crate or `std::time` + manual local offset via `libc` is messy — add `chrono = "0.4"` to the UI crate.
5. Add `overlay_module` toggle respect + a simple slider in the settings UI panel (can be a small addition to the dashboard; full settings panel styling optional here).

**Verify:** dev run: enable → screen visibly warms, ALL clicks pass through to apps beneath (test: click a terminal under the overlay and type), disable → gone. Warmth slider changes tint live.
**If it fails:**
- Wayland: `always_on_top`/fullscreen-over-everything may be compositor-limited. If the overlay doesn't cover panels on GNOME Wayland, accept covering the work area only, and record the limitation in STATE.md. If clicks do NOT pass through on Wayland (`set_ignore_cursor_events` no-op), gate the feature: only offer it on X11 (`XDG_SESSION_TYPE`) and show "Overlay requires X11 on Linux" in UI. Do not hack at the compositor.
- Transparent window renders black → WebKitGTK compositing: set env `WEBKIT_DISABLE_COMPOSITING_MODE=1` in `main.rs` before building the app and retest.

**Commit:** `Comfort overlay: click-through warm filter window with grain and auto schedule`

## Step 2 — Active-window context tracker (2.2a) `[ ]`

**Goal:** Log the active window's title+app every 5 s into a local SQLite DB.

**Files:** new `aegis-core/src/context.rs`, `aegis-core/Cargo.toml` (+`rusqlite = { version="0.31", features=["bundled"] }`)

**Instructions:**
1. X11 path (works when `XDG_SESSION_TYPE=x11` or XWayland fallback): shell out to `xprop -root _NET_ACTIVE_WINDOW` then `xprop -id <id> WM_CLASS _NET_WM_NAME` and parse. No new heavy deps; wrap in `fn active_window() -> Option<(String /*app*/, String /*title*/)>`.
2. Wayland: `active_window()` returns `None` (log once "context: wayland session — active-window unavailable"); the module stays functional but idle. Record limitation in STATE.md.
3. Sampler: `pub fn start_context_loop(stop: Arc<AtomicBool>)` thread, every 5 s read `active_window()`, write to SQLite at `~/.local/share/aegis/context.db`, table `samples(ts INTEGER, app TEXT, title TEXT)`. Batch-insert, WAL mode.
4. Tauri command `get_context_summary(hours: f64)` → top apps by time with per-app seconds (GROUP BY app).

**Verify:** `cargo test -p aegis-core context` — add a unit test for the xprop parser with captured fixture strings (hardcode two real xprop outputs). On X11, run the daemon 30 s, then `sqlite3 ~/.local/share/aegis/context.db 'select count(*) from samples;'` ≥ 5.
**Commit:** `Context tracker: X11 active-window sampling into SQLite with summaries`

## Step 3 — Intent classification (2.2b) `[ ]`

**Goal:** Classify current context into Deep Work / Research / Distraction / Idle with an explainable rule engine (a tiny local model can replace it later — keep the interface).

**Files:** `aegis-core/src/context.rs`

**Instructions:**
1. `pub enum Intent { DeepWork, Research, Distraction, Idle }` + `pub fn classify(app: &str, title: &str) -> Intent`.
2. Rules (lowercase substring match, first hit wins):
   - Distraction: `youtube`(unless title also has `tutorial|course|lecture`), `netflix, twitch, tiktok, instagram, facebook, twitter, x.com, reddit`(unless `r/rust|r/programming`), `steam, game`.
   - DeepWork: `code, vim, nvim, emacs, intellij, pycharm, terminal, konsole, alacritty, kitty, blender, figma, davinci`.
   - Research: `stackoverflow, github, docs., documentation, arxiv, scholar, wikipedia, chatgpt, claude`.
   - Fallback: browser with anything else → Research; unknown app → DeepWork if keyboard-active else Idle (keyboard activity arrives in P4; until then fallback DeepWork).
3. Store intent with each sample (new column, `ALTER TABLE` guarded by version pragma `user_version`).
4. Command `get_intent_now()` and include today's intent split in `get_context_summary`.

**Verify:** unit tests: ≥10 (app,title,expected) cases covering every rule branch including the youtube-tutorial exception.
**Commit:** `Rule-based intent classification with per-sample storage and summaries`

## Step 4 — Phone detection (2.3) `[ ]`

**Goal:** Detect a phone held in front of the camera at ~2 fps; emit a distraction event after 10 s continuous presence.

**Files:** new `aegis-core/src/objdet.rs`, `aegis-core/Cargo.toml` (+`tract-onnx = "0.21"`), model file in `models/`

**Instructions:**
1. Model: download **YOLOv8n** exported to ONNX (input `1x3x640x640`, 80 COCO classes; class 67 = "cell phone"). Any yolov8n.onnx export works. Place at `models/yolov8n.onnx`. If download requires a browser, ask the user to fetch it and place it there — give them the exact expected sha-agnostic check: `python3 -c "import onnx"` not needed; verify by file size 12–14 MB.
2. `objdet.rs`: load with tract (`tract_onnx::onnx().model_for_path(..).with_input_fact(..f32, [1,3,640,640])..into_optimized().into_runnable()`). Preprocess: letterbox the RGB frame to 640×640 (pad gray 114), NCHW, /255. Postprocess yolov8 head `1x84x8400`: for each anchor, class score = max of 80; keep score>0.35 & class==67; boxes cx,cy,w,h → xyxy, un-letterbox, NMS IoU 0.45.
3. Wire into `camera.rs`: every Nth frame such that cadence ≈ 2 fps (N = round(fps/2) with measured fps), send a copy of the frame to a dedicated detection thread (same non-blocking `sync_channel(1)` pattern as face detection — NEVER block the capture loop). Track `phone_visible_since`; after 10 s continuous, set `phone_detected: true` in `VitalStats` (add field + payload passthrough) and log the event into the context DB (`app='__phone__'`).
4. Config toggle `phone_module` default off (model is optional — if `models/yolov8n.onnx` missing, module reports unavailable, app runs fine).

**Verify:** add `bin/test_objdet.rs` that runs one image (extract a frame with a phone via ffmpeg from a quick user recording, or any COCO image file path passed as arg) and prints detections. Manual live test: hold your phone up ≥10 s → UI badge appears; put it down → clears within 3 s. CPU: `top` — added load < 15 % of one core at 2 fps (tract yolov8n ≈ 60-150 ms/frame on CPU; at 2 fps that's fine but if >200 ms, drop cadence to 1 fps).
**If it fails:** tract can't load the model (unsupported ops) → use YOLOv5n ONNX instead (simpler ops, output `1x25200x85`, class 67; adjust postprocess: obj_conf * cls_conf). If both fail, mark step blocked in STATE.md — do NOT ship a broken module.
**Commit:** `Phone-in-frame detection via YOLO ONNX at 2fps with distraction events`
